## 2. 分解方式：主线 → 对象 → 一个可验收结果

### 2.1 任务层级

```text
全站品质目标（不是一个无限扩张的运行 Goal）
  ├─ 工作流主线：交互 / 资产 / 复现 / 服务 / 跨端……
  │    └─ 任务 ID：一个结果、一个负责者、一套最小验收依据
  │         └─ 必要时按页面、角色、规则或故障场景继续拆子项
  └─ 批次 B01、B02……：选定一组任务，在一个明确候选版本上集成
```

批次只组织交付，不复制任务状态。不把所有工作串成一条必须整站完成才能交付的流水线，也不按文档顺序机械执行。

### 2.2 什么算“足够细”

一个可进入执行的任务应同时满足：

1. 能用一句话说清结果；存在明确的交付物和能否通过的判断。
2. 一个实际负责者能控制主要写入面；跨角色合作有明确接收点。
3. 未完成时仍能留下有用产物、具体阻塞和一个下一动作。
4. 不将互不依赖的多个页面、角色或规则强行捆绑；不将每次读文件、截图、跑命令拆成任务。
5. “核实问题”“作出产品决定”“实现结果”不能互相冒充完成；局部改进的必要验证属于该任务，不额外制造一条验证流水线。

出现“所有”“全面”“多项同时”等范围，入队前须进一步明确对象。例如 `CON-02.tideAware`、`UX-09.shop`；保留原 ID 为父项，父项改为汇总，只有子项计入叶子任务进度。拆分后的硬依赖同步指向实际所需子项，不能仍要求无关对象全部完成。

### 2.3 两类可复用对象流水线

角色和主题已在账本中按具体对象预展开，每个对象三项：

| 阶段 | 工作 | 完成的含义 |
| --- | --- | --- |
| `R`：核实 | 对照目标版本、现状及品质准则，定位差异；说明权利/平台条件 | 有可复查结论和该对象的保留/改进判定，不等于艺术优化已完成 |
| `C`：条件性改进 | 只处理该对象已批准的差异，不顺带改玩法或其他对象 | 实际产物达到该项约定，局部证据完整；是否纳入候选版本另有记录 |
| `V`：目标端验收 | 在明确版本与实际宿主中核对身份、状态/空间和操作关系 | 对该对象形成可复查结论；离线渲染和文件存在不能代替运行画面 |

`R` 证明现状已满足要求时，`C` 可经记录判为“不适用”，`V` 仍核对保留后的实际体验。必要输入、设备或操作授权不足时，相关步骤进入阻塞，不能用“不适用”绕过。来源权利待核实的资产可继续在既有授权内做核实与视觉观察，记录限制；视觉通过不等于取得修改、再分发或发布许可。

按对象推进：阿玛拉受阻不影响奶蛙或档案单位；某个草稿主题暂缓不阻止已选主题交付。若某角色还要制作模型、动作和肖像，进入 `C` 前按实际交付边界拆子项，不把三种产物藏在一个含糊的完成标记里。

## 3. 任务卡与状态规则

### 3.1 每项最低追踪字段

账本保留 ID、来源、依赖、预期结果、状态和记录链接。任务激活时再创建详情记录，**不为全部候选项预造空文件**。

建议记录目录：`docs/site-optimization/records/<任务ID>.md`，尚未创建。任务结果为代码/美术时，产物仍位于项目正常目录，记录只负责引用。

```text
任务 ID / 父 ID / 任务定义版本：
来源：审查 A/T 方向 + E/V/B 证据；新增任务写发现来源
目标：平台、源码提交/基线、必要的配置与制品标识
本项范围 / 明确不包含的内容：
实际负责者 / 接收或评审者 / 允许写入范围：
依赖：消费哪项输出及其版本；哪些决定或授权已经具备
验收：可观察结果、保留要求、必要负面路径；未定阈值及确定者
交付：文件/提交/制品/决定链接；集成位置或尚未集成
证据：步骤与输入、宿主/环境、结果、限制、持久文件链接
执行记录：时间；动作与目标；结果（含失败）；运行回执/子会话引用
阻塞：具体缺口、解除责任方、解除条件；当前安全停点
下一动作：一个可执行检查或操作
验收结论：谁在何时依据什么接受/退回；剩余问题对应哪个 ID
```

这不是要求每项都加数据库、截图、性能测试。与本项无关的字段写“不涉及”；小任务可以一段记录完成。状态只改账本，详情记录不维护另一份可漂移的状态表。

### 3.2 状态与转换

| 状态 | 含义与退出条件 |
| --- | --- |
| 拟定 | 设计候选；未获本项执行资格。先确认范围、目标与输入 |
| 就绪 | 在授权批次内；硬依赖已满足，范围/负责者/验收/必要条件已明确 |
| 进行中 | 已由负责者开始；必须能指出当前产物及下一动作 |
| 待验收 | 产物和必要证据齐备，等待接收；不是“等测试跑完” |
| 已验收 | 约定结果被接收，证据可定位；只证明记录中的版本与平台 |
| 阻塞 | 缺条件无法继续；记录解除方与条件。解除后复核输入再回就绪 |
| 暂缓 | 产品/批次有意延后，保留原因与重新考虑的触发条件 |
| 不适用 | 有可追溯的“不需做”判定；不计作改进完成 |
| 已替代 | 被新任务替换或拆分；必须指向继承 ID，历史不删除 |

正常路径：`拟定 → 就绪 → 进行中 → 待验收 → 已验收`。验收退回则回到“进行中”，注明未满足哪条标准。对已验收项发现回归，追加复核/修正子项并使受影响的批次验收待复核，保留旧结论的版本，不篡改历史。

**硬依赖满足**通常需要上游“已验收”的指定输出。接收任务也可明确接受特定条件项的“不做判定”，但需记录判定依据、决定者、保留产物和适用版本。例如对象 `V` 可接收该对象 `C` 的“不适用”，`REL-01.B01` 可接收本批已决定保留的条件改进结果；均不将任意“不适用”自动视作依赖成功。该判定仍不计为实施完成。上游因范围变化被替代、撤回或不再适用于目标版本，下游重新核对相应关系。

### 3.3 身份、证据与完成不可混淆

- 任务 ID 一经引用不改名复用；范围细化增加子 ID，替换记录前后关系。
- 时间写时区；有提交用提交，没有提交的在制输入写工作树及相关变更清单，不虚构版本号。
- 一张图证明一个状态；一条成功响应证明一个接口阶段；运行回执证明动作发生。完整业务结果需要对应状态关系的证据。
- 代码已验收但还在独立分支，不能被当作候选制品已拥有。消费者需能访问并明确纳入对应提交/资产；交付位置写在记录中。
- 证据失效按影响判断：相关逻辑、资源、环境或配置变化后复核对应结果；不因无关改动强制重跑全站，也不以旧证据覆盖新目标。

## 4. 依赖、授权与分批推进

### 4.1 三种关系

1. **硬依赖**：没有该输出无法定义或判断本项；列在账本，可组成有向无环图。
2. **条件门槛**：如对应素材许可、产品决定、设备可用、真实服务授权；写在任务卡，只阻塞相关任务。盘点许可材料的任务验收不等于取得许可。
3. **参考输入**：风格判断、测量方法、相邻任务结果；可并行获取，不误写成阻塞。

所有非 `WF` 项拟定为继承 `WF-02` 的激活条件，表中不重复。`WF-02` 只批准所列任务与目标，不是一次批准整个账本。新增批次重核同样的入口条件，并在批次记录中引用新的决定；旧激活记录不扩大到新范围。

### 4.2 分批选择方式（首批已选，详见 B01）

| 类别 | 候选 | 选择理由 / 需要避开的误解 |
| --- | --- | --- |
| 局部已知问题 | `UX-01` 指标、`UX-02` 余额显示、`UX-03` 模态范围 | 已有直接证据，边界小；先复核目标版本即可，不依赖完整美术或经济改造 |
| 角色承诺样板 | `CHR-ama-R` 起的一条对象链 | 同时暴露展示与出战差异；先定目标端、品质与权利条件，不默认搬入 B 资产 |
| 跨系统保证 | `VAL-01`、`REP-02`、`SVC-01` | 先确定消费、版本与结算保证，再进入相应实现，避免技术方案替产品决定 |
| 证据缺口 | `PERF-01`、`FEEL-01`、某个 `SCN-*-R` | 先取有区分力的证据；不因为有优化条目就必须改动 |

这几类是可选通道，不是四个固定阶段。首批规模由写入冲突、可用评审/设备与授权决定，不设置固定并行数、小时或自动重试次数。

### 4.3 并行与集成规则

- 一个任务一个实际负责者；评审归属沿用 CONTRIBUTING，不能把文档中的“角色”当作已向某位协作者派工。
- 只并行输入已明确、写入不冲突的工作。共同配置、角色映射、总装、公共 API 及同一素材文件由负责集成的人协调，不让两个分支各自覆盖。
- 发现共享接口影响时，先记录最小契约与消费方，等待真正需要的评审；不据“全站优化”顺带全面重构。
- 可读取 B 参考，但复用其成果时逐项记录来源、权利、适配差异与纳入提交；不把整个脏工作树当作可合并产物。
- `REL-01/02` 按批次实例化为 `REL-01.B01`、`REL-02.B01`。候选只包含已列明任务；存在不相关阻塞不自动阻止该批交付。

## 5. 验收：每项先能判对错，再谈完成

### 5.1 入队条件

范围和对象确定；输入版本可定位；负责者/写入面清楚；硬依赖可消费；验收可观察；涉及的产品/权利/服务门槛具备。性能目标等尚未有依据时，先执行测量/决定项，不把“提升一些”当作改进验收。

### 5.2 分类型的最小证据

| 类型 | 最小有用证据 | 不能单独当作通过 |
| --- | --- | --- |
| 已知逻辑/显示问题 | 原行为关系、目标版本的修正结果、一个能拒绝旧错误的聚焦检查 | 编译通过或只看新文案 |
| 消费/任务/结算 | 操作前后数据、相关写入或时序边界、用户结果；针对真实边界的失败检查 | 钱包单次写入成功、HTTP 200 |
| 角色/主题/UI | 同对象、可比条件下的前后画面；需要时连续操作；说明保留的艺术特征与差异 | 文件存在、离线精修图、单纯主观“更好看” |
| 配置/复现/契约 | 生产者与消费者一致，合法/非法输入或已知回放得到可解释结果 | 改 schema 文本、批量更新 golden |
| 性能/容量 | 相同场景与环境的基线/结果、目标阈值的依据、主要代价 | 包体减少、一次截图或平均 FPS |
| 跨端 | 对应平台与版本的真实运行关系；缺设备/Cloud 时明确停在什么层级 | Web 通过、离线图或 WX 构建成功 |
| 决策/盘点 | 决定者、适用对象、依据、保留/不做项及受影响后继 | 文档存在即假定决定已获接受 |

数值指标在相关测量项中按目标设备和真实场景确定；艺术评价以现有轻快卡通/海滨语境为依据，保留差异，不添加“必须写实/统一身高/更多特效”等条件。

代码任务遵守仓库聚焦测试与 `npm run check`；Web 集成加构建和真实浏览器观察；WX 加实际目标端证据。文档、盘点和权利材料任务按结果核对，不为它们机械运行全套游戏检查。跨任务 `QA` 负责关系与缺口，不替每个任务重复验收。

### 5.3 任务结束与批次结束

- **任务结束**：约定结果/证据/接收者齐备，记录输入和交付位置，剩余项有 ID；不得把重要未满足标准改成“以后再看”后仍记已验收。
- **批次结束**：选定叶子项已验收或有明确不做决定，候选中确实包含相应产物，关键交叉关系通过。范围外 WX、草稿主题、未来收费等不作为本批隐藏门槛。
- **发布是单独结果**：本地验收、合并、推送、候选就绪、正式上线分别记录。本批可停在候选就绪，不自动产生生产发布义务。

## 6. 可持续推进与中断恢复

### 6.1 每轮闭环

```text
读取目标与上轮停点 → 核对版本/依赖/写入归属
→ 选一个明确动作 → 执行并观察核心结果
→ 记录产物、失败、限制 → 更新账本
→ 接收 / 继续一个下一动作 / 等待明确条件
```

每轮不必都改代码或产出大报告；一次有效定位、明确无须改动、确认阻塞都可推进任务，但不能计为实施已完成。新发现先挂到原方向和证据，判断是否影响当前验收，再决定本项修正或另建候选，避免无限扩展范围。

### 6.2 持久记录与交接

- 关键结论及必要证据链接留在仓库或约定的持久制品位置；`/tmp`、会话消息和运行器回执只是定位线索，不能成为唯一恢复入口。
- 小图/摘要按需保留；大视频或日志只保存必要片段/制品引用，不复制所有临时文件或建立额外哈希链。
- 中断前能保存时，记录当前任务、实际修改、完成的检查、未完成操作、负责的后台进程/子会话和下一动作。
- 恢复先核对这些产物、实际分支状态及原生任务回执；未收到通知不表示失败或成功。只等待自己持有的后台工作时使用事件等待，不轮询模型进度。
- 子任务回报须包含范围、实际结果、证据、未完成项和产物位置；主负责人接收整合，不能用“子会话已结束”替代验收。

### 6.3 阻塞处理

| 情况 | 当轮处理 | 可以继续什么 |
| --- | --- | --- |
| 产品语义未定 | 问一个有依据的聚焦问题，记录决定影响哪些 ID | 已明确语义的独立项 |
| 权利或素材来源缺证 | 标出具体输入及派生物，等待有效材料/范围决定 | 只读盘点及不依赖该素材的项 |
| 真实 WX/Cloud/设备不可用 | 记录已达到的验证层级，不升级为目标端完成 | 本地可完成的独立实现/检查，保留目标端验收项 |
| 观察路线失效 | 区分捕获失败与产品失败，采用可行等效观察或明确缺口 | 原要求仍成立的其他检查 |
| 方法反复不产生信息 | 保留产物，改变假设或缩小对象，不重复同样尝试 | 可以区分剩余原因的一次动作 |
| 共享文件冲突/版本漂移 | 先协调归属，确认最新共同输入 | 无写入冲突且输入有效的项 |

解除阻塞需要实际条件满足，不能只靠定时重试。授权暂停或用户改变范围后，重新确认下一步，不能按旧计划自动扩大执行。

## 7. 可追溯与进展视图

最短追溯链：**审查方向/证据 → 任务 ID → 决定/版本 → 产物 → 验收证据 → 候选/发布记录**。反向从一处提交或画面，也应能找到任务及原始理由。

任务详情中的决定用 `<任务ID>-D01` 编号，证据用 `<任务ID>-E01` 编号；只编号实际产生的记录。说明由谁接受、作用于哪些对象与版本，后续改判新增条目，旧条目标注被谁取代。

每批汇总只需回答：

1. 已选哪些叶子任务，各处于哪种状态；哪些结果已经被接收？
2. 哪些产物已在候选中，哪些只在独立分支，哪些已发布？
3. 阻塞是什么、需要谁提供什么，独立工作是否还能继续？
4. 还有哪些重要证据缺口，下一动作是什么？

不以完整候选账本作为完成率分母；只报告本批固定范围的叶子状态数。“不适用/暂缓/替代”单列，不能充当优化成功。范围调整需记录新增/移除，父项和子项不重复计数，避免拆得越碎越像进展更快。

## 8. 长任务运行器的接入边界

以下是运行规则；当前已接入保存 Goal，实际动作和结果仍以原生回执、任务账本及批次记录为准：

- 一次运行 Goal 承载一个已授权批次或一个独立任务，并写清包含/不包含的 ID；不是对整份候选账本的无限实施授权。
- 运行目标明确结果、停点和人工决定门槛；文档/账本保存任务语义，原生队列保存执行动作，避免维护第二份独立任务树。
- `continue` 只在有明确且获授权的下一动作时使用；`waiting` 对应已登记后台工作；需要决定或条件时报告 `needs_input`；满足约定结果才 `complete`。长期推进没有靠固定轮数/时长自动证明完成的规则。
- 运行报告的 `evidence` 引用实际已完成操作 ID；文件存在/包含检查仅证明形式条件，不能代替第 5 节的业务、视觉与目标端判断。
- 暂停/恢复与本地任务状态分开：运行器暂停并不证明原生进程已停止。恢复前对账；文档写“就绪”也不会自行恢复 Goal。
- 默认按需运行；只有确有长期外部事件且获得相应授权时才考虑监视/定时唤醒，不因“长任务”默认建立永久监听。

## 9. 本设计如何维护

- 计划建立时所有任务为“拟定”；后续状态只在账本更新，不把设计定义数量视为实际完成数。
- 每批激活均核对 `WF-01/02` 对应的范围与入队条件；不必重新做整轮全站审查，只复核会改变该批判断的输入。
- 新发现追加稳定 ID 和来源；大项拆分、取消或换方法均保留理由与继承关系；变化只传播到真正受影响的任务。
- 设计验收只证明方向覆盖、任务可定位、依赖无环、状态/授权清楚、结果可判断、证据可续接；优化项的真实完成另由各项记录支撑，不能反向由计划文本推定。
