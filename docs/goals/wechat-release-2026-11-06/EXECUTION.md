# 后续 Goal 执行建议

用户要的是可上线的游戏，不是计划书或展示页。以下阶段用来减少返工；除真实外部依赖外，不要求每一步都等待用户确认。

## 1. 推进顺序

| 阶段 | 实际交付 | 判断阶段完成的证据 |
| --- | --- | --- |
| M0 基线与目标 | 保护当前修改；核实 AppID/微信目标、云环境/预算、设备条件；确定首发功能与页面地图；记录现有场景氛围 | 源码状态、简短决策记录、明确的阻塞项；不是重复抄本准备包 |
| M1 微信完整一局 | 以现有玩法/素材打通启动→大厅→选角→跑局→死亡结算→重开；修复配置/分包链；接通最小可信云身份与一次数据读写 | 开发者工具与可用真机观察；目标云环境实际请求与读回结果。暂缺外部条件时准确标记部分完成 |
| M2 权威数据闭环 | 云端身份、玩家存档、统一钱包/拥有状态、任务/手册奖励、结算校验、排行榜；完成持久化与幂等 | 正常跑局产生合法进度；领取后余额/库存一致；重进、跨设备、重复请求与越权路径结果正确 |
| M3 产品与非跑酷 UI | 大厅、角色、福利手册、任务、商店/仓库、排行、设置、结算等首发页面；可达入口、完整反馈与导航 | 微信内实际操作全链路；关键页面截图；长文本、滚动、安全区及错误状态可用 |
| M4 角色与细腻场景 | 角色建模/动作升级；氛围提取后的场景重设计；资源加载、渲染优化 | 同一实际跑局中观察动作、碰撞与场景连续性；前后画面对比；代表设备性能记录 |
| M5 发布交付 | 可导入/上传的小游戏包、目标云部署、资源清单、必要配置与上线说明、合规材料清单 | 构建/逻辑检查、开发者工具、真机、真实云数据分别验收；剩余平台手续逐项列明 |

M1 是风险消减用的最小切片，不是整个任务的最终成果。M2 契约稳定后，非跑酷 UI、角色资产、场景表现可以按文件归属并行；不要等所有 Web 美术做完才第一次碰 WX。

### 技术路线选择

- 优先验证当前 Three.js + 平台适配 + 共享自绘 UI 的微信可行性；把 Web DOM 作为功能和设计参考，在目标渲染体系中实现页面。
- 若工具、兼容性、资源管线或维护成本暴露出实质障碍，比较 Cocos 等目标端路线后作出有依据的选择。迁移可复用 core/config/规则测试，不默认重写确定性模拟。
- 只实现选中的交付路线，不同时维护两套新产品。引擎更换若需要大规模工具安装或改变已确认的项目选择，先说明收益、成本及需要用户决定的部分。

## 2. 产品闭环：候选首发方案

下列是贴合已有功能的推荐设计，执行时可合理调整；并非用户已逐项确认的额外需求。

### 福利手册

推荐定位为**免费成长与福利领取手册**：用少量清晰章节串联新手目标、跑酷里程碑和已存在的日/周任务；签到可在确有价值时加入，首版不依赖付费战令或广告。

- 每项奖励说明条件、进度、奖励内容与去向；章节/阶段有清晰完成感。
- 状态明确：未解锁、进行中、可领取、领取中、已领取、失败可重试。只有真正可领取时才显示领取红点。
- 任务与手册若引用同一目标，复用进度，不重复计奖；独立奖励使用独立、稳定的发放标识。
- 服务端时间决定周期；跨日、过期、离线后重连不能依靠本机时间刷奖励。
- 领取必须真实改变统一钱包/库存；回大厅、进商店、重启与同一微信账号换设备后结果一致。
- 首次成功后响应丢失，再点领取应返回已有结果而非二次发放。UI 按钮防连点只是体验，数据库原子性才是发奖边界。

### 经济、商店、仓库与角色

- 建立唯一权威经济状态。明确跑局收入、任务奖励、手册奖励、消费及角色/皮肤授予的入账规则。
- 推荐先完成游戏内货币的确定性购买/兑换与装备，不把支付、抽奖、充值或真实价值奖励作为默认前提。
- 若上线商店，必须有价格、拥有状态、余额不足、确认、成功与失败状态；服务器扣款与授予同一事务提交，重复购买按商品语义处理。
- 仓库展示实际拥有物与装备结果；角色选择读同一份拥有状态，技能说明、模型、头像和实际出战一致。
- 首发解锁方案要考虑当前角色已可选择的事实，不盲目按旧配置价格把所有角色重新锁住。明确新玩家初始拥有、旧测试数据处理以及未实现来源的替代获取方式。
- 本机余额/旧游客数据是否迁移须先核实真实用户与业务需求；不能直接相信任意本地数值并导入正式经济库。

### 其他页面

- 保留既有跑酷、角色技能、任务、首次金币前排行榜与主题能力，修复目标端接线。
- 大厅突出“开始酷跑”，角色切换与福利领取次之；活动/成就等占位入口可在首发收起，或实现一个真实且有限的版本。
- 不以隐藏福利手册、关闭任务/排行、删掉角色优化等用户核心目标来缩减验收。
- 设置中每个开关都必须实际生效。新手操作说明、返回位置、结算后下一步和云端失败提示属于直接支持可玩性的完善。

## 3. 非跑酷 UI 设计方向

推荐方向：**海滨冒险俱乐部，清爽卡通与轻量实体质感**。沿用“雷霆酷跑”品牌，让大厅、角色、手册与场景属于同一个世界；不拘泥于旧 CSS、卡片排布或背景构图。

- 视觉层级：奶白/暖沙作基底，海蓝作结构与导航，珊瑚/暖金突出主要操作与奖励；深色文字保证清晰阅读。减少没有功能含义的装饰堆叠。
- 大厅以角色和开始按钮形成核心画面；次级入口分组，减少一屏堆满功能按钮和红点。
- 角色页强调形象、技能、拥有/出战状态；立绘与模型相互对应，操作不被大图遮挡。
- 福利手册可用章节页签、里程路线与奖励格表达进度；“书册”只是设计语言，不强制复杂翻页特效。
- 商店/仓库用同一套物品图标、品质颜色与信息密度；获取途径和装备状态无需猜测。
- 结算区分整局成绩、首次金币前榜单成绩和本局收益/同步状态，避免把不同数字都叫“得分”。
- 统一按钮、弹层、加载/空/失败状态、触控反馈和返回行为；弹层打开时不让触摸穿透触发底层开跑或领奖。
- 适配微信胶囊、安全区、窄屏和文字长度。中文字体覆盖与新增文案同步处理，不能只依赖桌面系统字体。
- 先完成一组有真实数据的代表页面并在微信查看，再推广组件；减少“代码很完整但目标端观感未看”的返工。

## 4. 角色与场景的实质升级

### 角色

1. 先核对首发角色 roster、现有 GLB 与缺失资产，明确各角色识别特征和体型关系。
2. 改善轮廓、面部/服装细节、材质层级与骨骼权重；不以只换色、只换头像替代建模优化。
3. 连续检查 Idle/Run、换道、起跳/落地、滑铲/起身、飞行、受击/死亡与技能反馈；脚底接地、速度与步频协调，避免抖动、滑步、突兀回弹或动作频繁打断跑步。
4. 保持显示尺寸、碰撞净空与玩法差异的关系；模型热替换、加载失败和缺资源需有合理处理，但回退不能掩盖首发资产缺失。
5. 以真实跑局与动作录屏验收；模型文件存在、clip 名字齐全只能证明结构。

### 场景

1. **旧场景删除/替换前**保存简短氛围说明与可用的现状画面证据：色温、明暗、空间层次、地标、动态、镜头、跑道可读性，以及哪些问题要修。先读 [BASELINE.md](BASELINE.md) 的初步提取。
2. 优先从微信最小运行链观察旧场景；已有可靠截图/录屏也可作参考。无法观察时标明来源限制，保留旧实现直到可以比较，不凭源码推断冒充视觉验收。
3. 推荐在原晴日海岸上重做近/中/远景：跑道近景清晰；沙滩与建筑中景有生活细节；海岸线、海面与远景建立纵深。细腻来自形状、材质、光照、层次与节奏配合，不是无限加 mesh。
4. 用海岸转折、建筑与设施的组合变化降低重复感；海、水线、浅滩、湿沙、石头、植物和室内陈设之间有合理接触与尺度。
5. 保留车道与障碍读取优先级；高速时仍能识别跳/滑/换道机会。避免装饰遮挡、穿插、循环接缝、整块跳变或丢帧。
6. 结合实际热点使用实例化、对象复用、按需资源、适当细节分级与移动端材质；真实设备观察画面和性能后再调预算。不要为追求截图细节牺牲跑局稳定性。

## 5. 验收方式

不建设 Web 测试站、不以 Web 作为交付前置，也不要求先把 Web 改好。保留必要的 Node 逻辑测试、确定性回放、配置/架构检查和微信构建；不为绕过失败删改测试或无解释更新 golden。

执行阶段通常使用：

```sh
npm test -- tests/<受影响的测试>.test.mjs
npm run check
npm run build:wx -- --minify
```

这些命令不构成目标端验收。实际证据应覆盖：

- **可玩链路**：微信冷启动、大厅、选角、完整跑局、结算、重开、回大厅；前后台切换、触控与音频合理。
- **产品链路**：完成真实条件→手册/任务领奖→余额/库存变化→消费/装备→再次读取一致。
- **真实边界**：重复/并发领奖、跨身份请求、篡改/过期票据、结算失败重试、调试局隔离；按涉及的真实风险选择检查，不做无关测试矩阵。
- **画面与动作**：非跑酷关键页面截图；角色连续动作、场景循环和高速可读性录屏。画面观察发现问题后修正，而非只存截图。
- **性能**：记录代表设备、微信/基础库版本、包体、冷启动、帧时间/卡顿及长局内存趋势。可先以流畅档 60fps、低档稳定 30fps 为讨论目标，再依据实际设备定预算；它们不是本轮已确认的硬指标。
- **微信与云**：在开发者工具及计划支持的代表 Android/iOS 真机上验证；确认目标云环境的身份和持久数据实际生效。云控制台部署成功不替代客户端读写成功。

首发功能、UI、美术、微信运行和云数据均有证据时，才可报告技术交付完成。账号权限、真机或正式环境缺失导致的未验收应标为部分完成/阻塞，不写成“已具备上线条件”。平台审核、备案及正式公开发布状态另列。

## 6. 续跑与协作

- 每轮报告简短列出实际修改、检查结果、剩余问题和具体下一步。失败尝试影响结论时说明，不只写“已优化”。
- 证据保存到任务自己的目录；记录对应源码版本与必要工作区差异、云环境和设备，不把旧截图嫁接到新版本。
- 并行任务给出文件归属、接口和预期交付；主代理负责整合与最终判断。采用已授权的集中模型路由，不自行更换模型或扩大费用。
- 缺账号/设备时先继续独立代码与素材工作；可执行内容都耗尽时再报 `needs_input`，给用户一个最小、具体的协助动作。
- Goal 的 `complete` 依据真实交付；文档存在、TODO 清空、子任务说完成或构建通过不能单独作为完成条件。等待自有后台任务用完成事件，不循环询问进度。
