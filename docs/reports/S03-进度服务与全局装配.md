## 关键实现决策（供主会话复核）

1. **shop.changed → shop.buy.count 的副作用隔离**：`ShopService.refreshIfNeeded()`/`list()` 跨天或惰性刷新也会 emit `shop.changed`（S02 已知行为），若直接 +1 会在跨天后产生虚假购买进度。装配层改为比较 `dailyBought/adClaimed` 计数快照，只有计数增加才分发 `shop.buy.count`；跨天清理（计数减少）忽略。跨天集成测试固化了该行为。广告领取（`claimAd`）计入该指标（按"商店行为"口径，见遗留问题 3）。
2. **`menu.activities` 红点口径**：按 docs/02 §4「存在可领取里程碑或时间窗内新活动」，`ActivityService.hasClaimable()` = 存在 `enabled` 且状态为 `active` 的活动（可领取必然要求 active，故并集即 active 存在）。领取后至活动结束前红点保持，属运营常亮设计；若主会话期望"领完熄灭"，只需改该方法一处。
3. **`WelfareService.refreshIfNeeded()` 为 no-op**：签到日与每日广告均由日期字符串与当前游戏日实时比较，无需重置字段；文档要求的调用点保留。
4. **`ActivityService.refreshIfNeeded()`**：维护内存状态基线，首次调用只建立基线，之后状态翻转（如活动开始/结束）emit `activity.changed`，供 UI/红点刷新。
5. **`run.finished` 分工**：TaskService.onRunFinished 负责任务 + stats（loginDays 除外）；AchievementService.onRunFinished 只推进成就；活动进度在装配层统一映射，避免服务互相依赖（docs/03 §2.3 的来源约定）。其余跨服务指标（shop.buy.count / character.upgrade.count / login.days）由 `trackAll` 同时分发任务/成就/活动。
6. **`createGameContext` 创建后立即 `refreshDaily()` + `redDot.refresh()`**：前者建立 `flags.lastGameDay` 基线并触发首启 `day.changed`（`loginDays=1`）；后者保证同日重启也完成红点首次计算（同日不触发 `day.changed`）。Boot 之后调用同日为空操作。`platform.init()/login()` 仍由 Boot 负责（docs/03 §2.1）。
7. **`useItem` 菜单可用性与预校验**：`runBuff` 效果要求 `useTargets` 含 `menu`，否则返回 `unsupported` 且不消耗道具（如 `revive`）；`unlockCharacter` 在消耗前预校验（已解锁→`already_claimed`、资源不足→`insufficient`、条件未满足→`locked`、角色不存在→`not_found`），失败不消耗道具；成功时按 docs/03 §2.6 调用 `character.unlock`（该角色自身的解锁费用照常结算，属契约规定行为）。
8. **`markDirty/flush`**：节流 500ms 单定时器（窗口内多次变更合并为一次落盘），`flush()` 取消防抖立即写入并更新 `updatedAt`；集成测试以假定时器验证 500ms 落盘与 `flush` 即时写。

## 遗留问题 / 需要人工验证

1. **新增 core 文件未附 `.meta`**：与 S02 同策略（避免并行会话 meta 冲突），编辑器首次打开工程会自动生成；如需提交可由主会话统一处理。
2. **活动进度无上限**：`ActivityService.track` 累加不 clamp 到最高里程碑（任务会 clamp 到 target）；不影响领取判定，如需上限可调整。
3. **广告领取计入 `shop.buy.count`**：`claimAd` 也会推进该指标（快照包含 `adClaimed`），按"商店行为"口径；若策划要求仅统计付费购买，只需把快照改为只累计 `dailyBought` 并同步任务描述。
4. **活动进度在活动结束后保留**（历史展示），仅不可再领/再推进。
5. **`claim` 未达标返回 `insufficient`**（FailReason 无 not_reached 常量）；未开始 `locked`、已结束 `expired` 的口径已测试固化。
6. **`RedDotService` 依赖具体服务接口**（`RedDotSources`），由组合根注入；测试用 stub + 真实服务双路径验证。
7. **`createGameContext` 内部自建 `Logger`**（按 app.debug 开关 debug 日志），未提供外部注入入口（未在契约签名内）；如 Boot 需要自定义 sink，可后续在 `CreateContextOptions` 增加可选 `log`。
8. **`save.loaded` 事件无生产者**：契约与 docs/03 §3 定义了该事件，但 `createGameContext` 返回前监听者尚未注册；如需使用（如云存档覆盖提示），建议由 S05/S10 明确触发时机（S03 未擅自发射）。
9. **存档形状校验过弱（S01 存量）**：`isSaveShape` 未校验 `welfare/shop/activities/achievements/inventory/flags/stats` 子结构，版本号正确的残缺存档可能绕过坏档恢复并在服务层抛错；建议后续会话补强并加回归。
10. **`.meta`/场景/UI 未动**，`npm run check` 的 cc 侧仍以既有 UI 文件为准。
