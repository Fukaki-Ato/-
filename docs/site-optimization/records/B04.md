## 2. SVC-01.missions：选定的结果保证

`B04-D01`：在既有有效期和周期条件内，已批准票据按签发时的模拟、配置、有效局阈值及输入预算复跑。服务端临时不可用不能伪装成客户端无效局，也不能以一次故障消费掉重试依据。

- 正常有效死亡局计进度；仍存活的截断局/太短局按原语义可返回 200 但不计任务。200 不等于有效局。
- 繁忙/超时仍为可重试错误；规则缺失、损坏、ABI 不支持或代码不受信任返回 **503**，run 保持 open，客户端原回放仍在队列。
- 相同 run + 相同回放重复结算不重计；已完成后更换内容仍拒绝。
- 原自然 TTL、跨日/跨周计入、身份和领取事务保持不变，不增加跨周期补领或无限期恢复承诺。

决定由主代理按已签发有效进度保护目标接收；没有改变奖励数值、成本或用户资产归属。

## 3. REP-02.online.missions：规则和代码一起绑定

`B04-D02`：只保存配置或配置摘要不足以复现旧模拟代码。根 build/check 在编译后，以已有构建期 esbuild 打包自包含 ABI-1 ESM，包含 RunnerSim 闭包、服务器回放循环与 STEP_DT；仅保留 Node 内建外部导入。

SQLite `replay_rulesets` 按规则保存一次：ABI、完整代码、完整 content、实际 minRunSeconds、maxFrames/maxActions，内容派生 SHA-256 ID。`runs.rules_id` 引用它。签发时获取当前合法配置的 JSON 快照；结算取票据引用，不改用当前新版本。

包的代码哈希、包含配置/阈值的 rules_id、B03 的本机存档格式 2、离线回放格式 2均不同，不能相互替代。客户端声明也不是服务端执行依据，HTTP 不接受源码/模块路径/rules_id。

### 代码信任不由数据库自证

哈希校验只证明数据完整性。执行前还要求代码 SHA 属于 SQLite **之外**的当前本地产物、封存基线或明确配置的历史发布哈希集合。测试即使往数据库放入一个 hash 自洽的新模块，也不会执行其顶层 sentinel，run 仍 open。

更多历史发布包可通过受控启动配置 `TRUSTED_REPLAY_RUNTIME_HASHES` 保留信任；不能自动信任数据库中自报的 hash。默认当前/基线之外的包暂缺信任时先 503，补齐可信配置后原票据成功结算，而不是删记录或切换到新引擎。
