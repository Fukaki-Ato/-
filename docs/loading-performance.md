# 启动加载优化

## 加载约定

- 8 个配置文件并发读取，各文件完成时立即校验、写缓存（不等待其他慢请求）；最终报告和错误仍按 `CONTENT_NAMES` 顺序汇总。
- Web 在准备 UI 时预取配置。UI 与游戏启动共用 `game.json` 的请求；启动结束后释放请求表，后续读取不使用启动期内存快照。
- 网络失败仍按文件回退本地缓存；网络返回坏配置时仍报错，不用旧缓存掩盖校验失败。
- 字体、配置、徽标、背景并行加载。视频成功时不再下载未使用的 `menu-bg.png`；视频失败或首帧超时仍回退静态图。
- JSON 使用 `no-cache`，允许服务端通过 ETag/Last-Modified 校验并返回 304。静态贴图和模型使用默认 HTTP 缓存策略，由服务端决定有效期；没有使用 `force-cache` 或永久内存缓存。
- WX 仅改变共享配置加载的并发度，资源路径、校验和离线回退契约不变。

## 受控浏览器对照

基线：`26c59cc`（`origin/main`）；优化：`fix/startup-loading`。
两边均使用生产 Web 构建和同一 Chromium，800×900 视口，每轮独立浏览器 context。
本地 HTTP 服务对每个请求增加 80ms 延迟，不做带宽限速；交替测量前后版本各 3 次。
耗时取导航开始到场景机进入 `select`（大厅），不以 `networkidle` 代替可交互状态。

| 样本 | 基线 | 优化 |
| --- | ---: | ---: |
| 1 | 3204ms | 1610ms |
| 2 | 3117ms | 1607ms |
| 3 | 3246ms | 1590ms |
| 中位数 | 3204ms | 1607ms |

中位耗时减少约 49.9%。同次观测中 `game.json` 从 2 次请求降到 1 次，
视频成功时静态背景请求从 1 次降到 0 次（少传约 2MB）。
浏览器同时验证了大厅 → 角色选择 → 奶蛙开跑及 GLB 动画就绪，以及视频加载失败的静态背景回退。

这些是本地受控测试，不是线上、真实弱网或真机 WX 的性能承诺。
视频首帧最多等待 4 秒、字体图集体积及主 JS 包大小仍是后续优化点。
